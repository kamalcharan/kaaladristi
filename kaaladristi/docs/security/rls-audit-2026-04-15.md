# RLS Audit Report — 15 Apr 2026

## Executive Summary

13 tables have RLS enabled. The frontend authenticates as `role=authenticated` via JWT.
The core issue discovered today: **RLS policies list `TO authenticated` but the Pipeline API
connects as `kd_app` (or `postgres` superuser) via DATABASE_URL — a different role.** PostgREST
queries from the frontend work because the JWT sets `role=authenticated`. Direct psycopg2 queries
from the Pipeline API work because they use a superuser or `kd_app` role which may bypass RLS.

**The km_industry_eod failure**: RLS was enabled with policies for `authenticated` and `anon`, but
the health check code uses `db._conn()` (PgClient/psycopg2) which connects as the DATABASE_URL role.
If that role is NOT a superuser and NOT `authenticated`/`anon`, RLS silently returns 0 rows.

---

## Authentication Architecture

```
Frontend (browser)
    ↓ JWT Bearer token (role=authenticated)
PostgREST (port 3000)
    ↓ switches to 'authenticated' role
PostgreSQL (RLS enforced per role)

Pipeline API (port 8100)
    ↓ psycopg2 via DATABASE_URL
PostgreSQL (role = vikuna_admin or postgres — superuser bypasses RLS)

Worker (python worker.py)
    ↓ psycopg2 via DATABASE_URL
PostgreSQL (same as Pipeline API)
```

**Key**: Frontend queries → `authenticated` role → RLS applies.
Pipeline/worker → superuser or `kd_app` → RLS bypassed (if superuser) or blocked (if not).

## Security Issues Found

### CRITICAL

1. **dc_inference — unrestricted write access**
   - Policy: `FOR ALL TO authenticated USING (true) WITH CHECK (true)`
   - Any authenticated user can INSERT/UPDATE/DELETE inference data
   - Fix: Change to `USING (public.is_admin()) WITH CHECK (public.is_admin())`

### HIGH

2. **km_index_constituents — write policy uses broken JWT claim extraction**
   - Uses `current_setting('request.jwt.claims')::json ->> 'role' = 'admin'`
   - Self-hosted JWT doesn't set `request.jwt.claims` the same way Supabase does
   - Silently denies all writes (safe but broken)
   - Fix: Replace with `public.is_admin()`

3. **km_industry_eod — RLS temporarily disabled**
   - Emergency fix from today. Must re-enable with correct policies.
   - Root cause: policies listed `authenticated` and `anon` but health check queries used
     `kd_app`/superuser role via PgClient

### MEDIUM

4. **GRANT ALL contradicts RLS intent**
   - Multiple tables have `GRANT ALL ON table TO authenticated, kd_app, anon`
   - This grants table-level permissions but RLS filters at row level
   - Confusing — prefer explicit GRANT SELECT/INSERT/UPDATE per role

5. **Reset token exposed in forgot_password response**
   - `kd_auth_forgot_password()` returns the reset_token in dev mode
   - Must remove before production

### LOW

6. **Inconsistent admin check pattern**
   - Most tables use `public.is_admin()` (correct)
   - `km_restructure_eod.sql` used `EXISTS (SELECT 1 FROM km_profiles ...)` (recursion risk)
   - `km_fix_rls_recursion.sql` fixed this for some tables but verify completeness

7. **VITE_ANON_KEY is empty**
   - Anonymous access effectively disabled
   - GRANT to anon role is redundant but harmless
   - Document as intentional

## Questions for Charan

1. **Which role does DATABASE_URL connect as?** Run: `SELECT current_user, session_user;` from psql using the same connection string.
   - If superuser (postgres) → bypasses all RLS (current behavior, probably fine)
   - If kd_app → RLS blocks unless policies include kd_app

2. **Is kd_app a separate role from authenticated?**
   - It appears in some GRANTs but not in any RLS policies
   - Should it be added to policies, or is it only used for direct PG connections?

3. **Should computed aggregate tables have RLS?**
   - `km_industry_eod`, `km_market_breadth`, `km_breadth_roc` are pipeline-computed
   - No user-specific data — RLS adds no security value
   - Recommendation: keep RLS OFF for these (simpler, no permission bugs)

4. **Should dc_inference writes be admin-only?**
   - Currently any authenticated user can modify
   - Is this intentional (collaborative editing) or a bug?
