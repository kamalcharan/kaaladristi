# Security hotfix — 26 Sep 2026 (migrations 226 + 227)

Companion to `rls-standard.md` and `rls-audit-2026-04-15.md`. Everything below was measured on the live `kaala_dristi_db` through the read-only MCP, not inferred from migration text — the two disagreed (see "What was open").

## What was open

| surface | live state before 226 | since |
|---|---|---|
| `kd_generate_token(uuid,text,text)` / `kd_sign_jwt(json,text)` | PostgreSQL default `=X` (PUBLIC EXECUTE). Via `/db/rpc/kd_generate_token` any caller, including the `anon` role, could mint an HS256 session token for any user id and any role, signed with `current_setting('app.jwt_secret')` | migration 003 (self-hosted auth) |
| `admin` role EXECUTE on both signers | explicit grant; `vikuna_api` (PostgREST login role) was a member of `admin`, so a request that could `SET ROLE admin` could still mint after 226 | migration 003 |
| Every `compute_*`, `refresh_*_catalog`, `maintain_fpb_active`, `compute_index_breadth`, snapshot and trigger function | PUBLIC EXECUTE (no migration ever ran `REVOKE … FROM PUBLIC` or `ALTER DEFAULT PRIVILEGES`); most also granted to `anon` by name | 014 onward |
| `anon` writes | `arwdDxtm` on `km_index_symbols`, `km_trading_calendar`, `km_pipeline_runs`, `km_fii_dii`, `km_rule_inference`, `km_api_sessions`, `dc_inference`, `dc_lookup`, `dc_market_status`, `kd_vani_opportunity_config`; `arw` on `km_equity_weekly` / `km_equity_monthly`; USAGE on 11 sequences | 004–134 |
| `anon` reads of user data | SELECT on `km_profiles` with **RLS off** (every email, phone, role, tier), `user_subscriptions` via a `USING (true)` policy, `km_admin_audit`, `km_vani_cache`, `vani_observation_cache`, `vn_interaction_log`, `km_api_sessions`, `km_config`, `km_jobs`. None of these grants exist in the repo migrations; they came from an off-repo blanket grant (grantor `vikuna_admin`) | unknown, before 2026-07 |
| `km_profiles` own-row policy | the SELECT/UPDATE policies in `km_profiles.sql:58-66` were **not present** live; only the two `is_admin()` policies were | — |

## What 226 closed (`km_migration_226_security_hotfix.sql`, applied 2026-09-26)

1. `REVOKE EXECUTE` on both signers from `PUBLIC`, `anon`, `authenticated`.
2. `REVOKE EXECUTE … FROM PUBLIC, anon` on 27 pipeline / maintenance / trigger functions; re-granted to `kd_app` (and the two trigger functions to `authenticated`, which writes the triggering tables).
3. `REVOKE INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER ON ALL TABLES … FROM anon` and `REVOKE USAGE, UPDATE ON ALL SEQUENCES … FROM anon`.
4. `REVOKE SELECT FROM anon` on the nine user / cache / ops / config tables above. **Market-data SELECT for anon is untouched.**
5. `km_profiles`: RLS enabled; `profiles_self_select` (authenticated, own row, SELECT only), `profiles_app_all` (kd_app + service_role), `profiles_readonly_select` (kd_readonly). No UPDATE policy for `authenticated` on purpose: profile writes go through `kd_update_profile`, so a direct PATCH now affects 0 rows.
6. `user_subscriptions`: `service_manage_subscriptions` (USING true) replaced by `subscriptions_service_all` for `service_role, kd_app`.
7. `ALTER DEFAULT PRIVILEGES FOR ROLE vikuna_admin / kd_app IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`.

Validated on a throwaway PostgreSQL 16 cluster before apply: login still works through the SECURITY DEFINER path, `kd_app` keeps its compute chain and subscription writes, a logged-in user sees one profile row and cannot self-update tier, rollback → re-apply clean.

## What 227 records (`km_migration_227_security_hotfix_followup.sql`, applied manually 2026-09-26 as `vikuna_admin`)

1. `REVOKE EXECUTE ON FUNCTION kd_generate_token(uuid,text,text), kd_sign_jwt(json,text) FROM admin;` — both signers now carry **only** `vikuna_admin=X`.
2. `REVOKE admin FROM vikuna_api;` — the PostgREST login role is now a member of `anon` and `authenticated` only. `vikuna_api` is created outside this repo (`PGRST_DB_URI`), so 227 guards on the role existing.
3. JWT secret rotation (ops script, in progress at the time of writing): `ALTER DATABASE kaala_dristi_db SET app.jwt_secret TO …` plus `ALTER ROLE {kd_app, anon, authenticated, service_role} RESET app.jwt_secret`. Recorded in 227 as a commented runbook with a psql-variable placeholder; the value is never in the repo.

## Exposure window and log evidence

- **Window:** from the day migration 003 went live (PostgREST `/db/rpc/` exposing `kd_generate_token` with PUBLIC EXECUTE) until 226 on 2026-09-26; for the `admin` path, until 227 the same day.
- **Logs checked:** `vikuna-nginx` access logs for `/db/rpc/kd_generate_token`, `/db/rpc/kd_sign_jwt`, `/db/km_profiles`, `/db/user_subscriptions` and `/db/rpc/compute_*`, excluding the known frontend flow. **Available range: 22–26 Sep 2026. No misuse found.** Logs for **1 Jul – 22 Sep 2026 are unavailable** (rotated out), so that part of the window cannot be confirmed either way; the rotation in 227 §3 is what closes it regardless.

## Where the JWT secret lives now

| copy | role |
|---|---|
| `/opt/vikuna/docker/docker/.env` → `JWT_SECRET` | shared compose; PostgREST reads it as `PGRST_JWT_SECRET: ${JWT_SECRET…}` (verification of every `/db/` bearer) |
| `/opt/vikuna/apps/kaaladristi/kaaladristi/.env` → `JWT_SECRET` | `kd-pipeline-api2` via `docker-compose.yml:48` (`lib/config.py:25` → `lib/auth.py:41`, verification of every FastAPI bearer route) |
| `kaala_dristi_db` database-level GUC `app.jwt_secret` (`ALTER DATABASE … SET`) | **single source of truth for signing** — read by `kd_generate_token` inside `kd_auth_login` / `kd_auth_register` |

The four role-level copies (`kd_app`, `anon`, `authenticated`, `service_role`) are RESET as part of §3. Before the rotation, the role-level values (md5 `aabc04fe…`, 86 chars) and the cluster-level value a plain session resolved (md5 `9316d2d4…`, 88 chars) did not match each other.

Rotation invalidates every issued session token (7-day `exp`); users log in again. Restart `vikuna-postgrest` and `kd-pipeline-api2` in the same step as the database `SET`, otherwise signing and verification disagree and every request 401s.
